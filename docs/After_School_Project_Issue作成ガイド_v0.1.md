# After School Project Issue作成ガイド

## 1. このガイドの目的

このガイドは、After School Projectの開発Issueについて、チーム内で書き方を統一するためのものです。

担当者が「何を作るのか」「どの状態になれば完成なのか」「何を確認すればよいのか」を理解できるIssueの作成を目的とします。

## 2. Issueタイトルの付け方

GitHubのタイトル欄には、このIssueで実現することを簡潔に記載します。

例：

- ログイン・ログアウトを実装する
- プロフィールを編集できるようにする
- 質問を投稿できるようにする
- 卒業生がお知らせを申請できるようにする
- イベントを申請できるようにする
- Neonへ接続できるようにする

`task:`や`[AUTH]`などの接頭辞は、チームでルールとして決定しない限り使用しません。

## 3. 共通Issueテンプレート

以下をGitHub Issueの本文へコピーし、対象機能に合わせて記入します。

```markdown
## 目的

このIssueで「誰が、何をできるようにするのか」を書く。

例：学校から発行されたアカウントで、利用者がログインできるようにする。


## 実装すること

このIssueで作る画面・機能・API・データ処理を書く。

- [ ] 例：ログイン画面を作成する
- [ ] 例：ログイン処理を実装する
- [ ] 例：ログアウト処理を実装する


## 対象外

このIssueでは作らない機能を書く。ない場合は「なし」と書く。

- 例：パスワード再発行は別Issueで実装する


## 関連する要件・設計

実装時に確認する要件や設計書を書く。関係しない項目は「なし」と書く。

- 要件ID：
- 決定ID：
- 画面ID：
- API ID：
- 関連テーブル：
- 関連する設計書：
  - `docs/ファイル名`


## 受入条件

このIssueを「完成」と判断できる具体的な条件を書く。

- [ ] 例：正しい情報を入力すると処理が完了する
- [ ] 例：必須項目が未入力の場合はエラーを表示する
- [ ] 例：権限のない利用者による操作を拒否する


## 確認方法

受入条件をどのような操作で確認するかを書く。

- 例：正しい情報を入力して、処理が完了することを確認する
- 例：未入力や不正な情報で、エラーが表示されることを確認する
- 例：権限の異なる利用者で、利用できる機能を確認する


## 依存関係・確認事項

先に完了する必要があるIssueや、まだ決まっていないことを書く。ない場合は「なし」と書く。

- 先行Issue：
- 関連Issue：
- 確認事項：
```

## 4. 各項目の意味

### 4.1 目的

このIssueを作る理由です。

「誰が」「何をできるようになるか」を記載します。

例：

> 利用者が、学校から発行されたアカウントでログインできるようにする。

### 4.2 実装すること

担当者に作ってもらうものです。

画面、ボタン、API、DB処理など、必要な作業を記載します。チェックボックスにすると、作業の進み具合も確認できます。

例：

- [ ] ログイン画面を作る
- [ ] 認証APIを作る
- [ ] セッションを保存する

### 4.3 対象外

このIssueでは作らないものです。

作業が予定以上に広がることを防ぎ、別Issueとの境界を明確にします。

例：

> ログインは実装するが、パスワード再発行は別Issueにする。

### 4.4 関連する要件・設計

担当者が実装時に確認する設計資料です。何を根拠に実装するかを示します。

- **要件ID**：必要な機能を表す番号
- **決定ID**：技術や運用について決めた内容の番号
- **画面ID**：実装する画面の番号
- **API ID**：使用または実装するAPIの番号
- **関連テーブル**：使用するデータベースのテーブル
- **関連する設計書**：詳しい仕様が書かれているファイル

すべてのIssueに全項目が必要とは限りません。関係しないものは「なし」と記載します。

### 4.5 受入条件

Issueを完成と判断する条件です。

担当者と確認者が、同じ基準で完成を判断できるようにします。実際の操作で確認できる具体的な文章にします。

例：

- [ ] 正しい情報でログインできる
- [ ] 間違った情報ではログインできない
- [ ] 権限のない利用者は管理画面を利用できない

### 4.6 確認方法

受入条件をどのように確かめるかを記載します。

- **受入条件**：どうなれば完成か
- **確認方法**：完成したことをどう確かめるか

例：

受入条件：

> 正しい情報でログインできる。

確認方法：

> 発行済みのIDと正しいパスワードを入力し、ホーム画面へ移動することを確認する。

詳細な単体テストやE2Eテストの手順までは記載せず、最低限の確認方法を示します。

### 4.7 依存関係・確認事項

ほかの作業との関係や、まだ決まっていないことを記載します。

- **先行Issue**：先に完了している必要があるIssue
- **関連Issue**：同じ機能に関係するIssue
- **確認事項**：チームで相談または決定する必要があること

例：

```markdown
- 先行Issue：NeonへのDB接続
- 関連Issue：ログアウト機能
- 確認事項：ログイン失敗時の表示文言
```

## 5. 各項目の役割

| 項目 | 書く内容 |
|---|---|
| 目的 | なぜ作るのか |
| 実装すること | 何を作るのか |
| 対象外 | 何を作らないのか |
| 関連する要件・設計 | 何を参考にするのか |
| 受入条件 | どうなれば完成か |
| 確認方法 | どうやって完成を確認するか |
| 依存関係・確認事項 | ほかの作業や未決定事項 |

## 6. Issueを作成するときの注意

- 1つのIssueに複数の大きな機能を詰め込みすぎないようにします。
- 担当者が1つの作業として進められる大きさを目安にします。
- 受入条件は「適切に動作する」のような曖昧な表現ではなく、確認できる状態を記載します。
- 関連する要件・設計が分からない場合は、推測せず確認事項へ記載します。
- パスワード、トークン、データベース接続情報などの秘密情報はIssueへ記載しません。
