## エグゼクティブサマリー

After School Projectは、IT専門学校における学校・在校生・卒業予定者・卒業生（OB・OG）のつながりを、卒業後も継続できるようにするクローズドなWebコミュニティの構想です。質問・技術交流・学校からのお知らせ・イベント告知を通じて、世代を超えた学びと交流の機会を生み出します。

## 実現したい３つの価値

| **柱**           | **提供価値**                                                             |
|------------------|--------------------------------------------------------------------------|
| つながりの継続   | 卒業後も学校や後輩との接点を保ち、関係性を一過性で終わらせない。         |
| 経験・知識の循環 | 就職活動の経験談、技術的な質問、在校生のプロジェクト協力を促進する。     |
| 交流機会の創出   | オンライン上の交流に加え、在校生と卒業生が参加できるイベントにつなげる。 |

## 初期方針

- 初期成果物はWebアプリ。学校と連携できる運用体制の確立もMVPの重要要素。
- 学校関係者と認証済みの在校生・卒業生が利用する非公開コミュニティを想定。
- 在学中に、OB・OGと在校生がつながるイベントを最低１回開催することを目指す。
- 将来的にはグループ校への展開が可能な汎用的な仕組みを目指す。

## 01 背景・解決したい課題

- 新しい学校のため、卒業生と在校生・学校が継続的につながる仕組みが十分にない。
- 就職活動の経験談や現場のリアルな情報を、先輩から直接得る機会が限られている。
- 技術的な知識や挑戦は学年・年齢を問わず共有できるが、交流のきっかけが不足している。

## 02 対象となる利用者

| **利用者区分**     | **想定する役割・利用方法**                                                             |
|--------------------|----------------------------------------------------------------------------------------|
| 在校生             | 質問・交流・イベント作成など。プロフィールはニックネームを基本とする。                 |
| 卒業予定者         | 卒業前から卒業生向け機能の一部を利用できる想定。卒業時は学校側が卒業生へ一括切替。     |
| 卒業生（OB・OG）   | 経験共有、質問への回答、お知らせ・イベント申請、後輩との交流。名簿への掲載は本人選択。 |
| 学校関係者・管理者 | 公式情報の発信、申請承認、利用者管理、通報対応など。                                   |

## 03 主要機能の全体像

| **機能**                 | **企画上の基本仕様**                                                                                 |
|--------------------------|------------------------------------------------------------------------------------------------------|
| プロフィール・卒業生検索 | 所属や卒業情報などを使って交流先を見つける。追加情報の公開・検索名簿掲載は選択制。                   |
| Q&A掲示板                | 技術・就職・制作などのテキスト質問と回答。コメントへの返信や解決済み表示を備える。解決後も回答可能。 |
| お知らせ                 | 学校公式のお知らせと卒業生からのお知らせを区分。卒業生による投稿・編集は承認制。                     |
| イベント                 | 勉強会・交流会等を告知。開催形式・日時・場所・申込先URLなどを掲載。アプリ内参加申込は行わない。      |
| アプリ内通知             | 質問への回答・コメント、申請の承認／却下など、必要な出来事を通知。                                   |
| 管理・安全対策           | 投稿通報、プロフィール非公開、アカウント停止、申請審査、履歴管理。                                   |

## 04 コミュニティ運営の考え方

学校管理者とアプリ管理者が協力して運営します。管理者の役割分担や任命は学校との協議を前提とします。学校管理者にはアプリ管理者より上位の権限を設ける方針です。

### 承認とコンテンツ公開

- 学校公式のお知らせは学校側が公開。卒業生からのお知らせは学校管理者またはアプリ管理者が審査する。
- イベントは学校関係者が直接公開可能。学生・卒業予定者・卒業生からの新規／編集申請は事前承認制。
- 公開済みイベントの編集審査中は従前の公開内容を維持する。イベント中止は主催者が即時反映でき、復元不可。

### イベント承認の運用ルール

- 承認専用画面を設け、初期表示は「承認待ち」、並び順は最初の申請日時が古い順。
- 専任担当者は設けず、学校管理者・アプリ管理者のいずれも承認・却下できる。重複確定を防ぐ。
- 開催日が過去となった承認待ち申請は自動却下しない。「開催日の修正が必要」と表示し、当日以降に修正するまで承認・却下とも不可。
- 開催日経過を理由とする追加のアプリ内通知は行わない。修正しても初回申請日時・表示順を維持する。

### 安全性と信頼性

- クローズドなコミュニティとし、認証された関係者以外には内容を公開しない。PoCでは学校発行IDと個別パスワードを使い、認証情報の個別配布・コマンド再発行を行う。詳細は[技術構成・認証方式決定書 v0.1](./After_School_Project_PoC_技術構成・認証方式決定書_v0.1.md)を参照する。
- 投稿・コメント・お知らせ・プロフィール等に通報機能を設け、管理者が事案を確認する。通報を受けただけでは自動非公開にしない。
- 必要に応じ、プロフィールを一時非公開とする、投稿を非表示とする、アカウントを停止するなどの対応を行う。
- 通報者には受付確認のみ表示し、対応開始／完了時の個別通知や通報履歴画面は設けない。
- 通報証拠・対応履歴・操作ログの保管と自動削除について、詳細ルールを別途定義済み。

> **設計上の留意点** 学校管理者・アプリ管理者の権限、本人確認、個人情報の取扱い、利用規約は学校側の確認を経て運用する。

## 05 MVP（初期リリース）の考え方

現時点で確定しているのは「Webアプリとして提供すること」と「学校と連携する仕組みを確立すること」です。プロフィール、Q&A、お知らせ、イベント等は主要機能として方向性が決まっていますが、初期リリースにすべて含めるかは未確定です。

## 06 想定する進め方

| **段階**             | **実施内容**                                                             |
|----------------------|--------------------------------------------------------------------------|
| 1\. 学校への提案     | 企画の目的、想定利用者、責任分担、運用・安全対策について合意を目指す。   |
| 2\. 成立条件の確認   | 在校生・卒業生の本人確認、卒業後のアカウント利用、学校の運営体制を確認。 |
| 3\. MVP範囲の確定    | 必須機能、対象ユーザー、優先順位、開発期間・体制を決定。                 |
| 4\. 設計・開発・検証 | 画面・データ・権限設計、実装、テスト、関係者による試用。                 |
| 5\. 試験運用と改善   | 在校生・卒業生の参加を促進し、フィードバックを踏まえて改善する。         |

## 07 主要リスクと検討事項

| **リスク／未決定事項**   | **対応の方向性**                                                                              |
|--------------------------|-----------------------------------------------------------------------------------------------|
| 学校から許可が得られない | 学校との協議を最優先し、責任範囲・メリット・情報保護の考え方を説明する。                      |
| 卒業生が集まらない       | 初期の参加者募集とイベントの実施、継続参加を促す仕組みを検討する。                            |
| 卒業後の本人確認・認証   | 学校配布のMicrosoft 365アカウントが卒業後に利用不可となる点を踏まえ、継続利用方式を設計する。 |
| MVP・技術・運用コスト    | 機能優先度、技術構成、維持費、学校側の運営負担を見積もる。                                    |
| 個人情報・運用ルール     | 規約、取得情報、管理責任、アクセス権、保管・削除を整理する。                                  |
| 詳細UIと一部機能仕様     | イベント承認画面の種類フィルター等、細部の仕様を順次確定する。                                |

## 08 直近の優先アクション

- 学校提案用の資料として本概要をレビューし、学校への相談・承認手順を確認する。
- 認証／本人確認方法と卒業後の継続利用方式を検討する。
- MVPに含める機能を確定して、開発計画・運用計画に落とし込む。

注記：本資料の「確定」は企画内での検討結果を指し、学校の承認や実装・運用開始を意味しません。
