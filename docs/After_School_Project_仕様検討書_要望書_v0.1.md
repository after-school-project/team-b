# 01 企画の要旨

**PROJECT SUMMARY**

After School Projectは、IT専門学校の在校生・卒業予定者・卒業生（OB・OG）・学校職員が、学校の承認を受けた関係者として利用するクローズドなWebコミュニティである。Q&A掲示板、お知らせ、イベントを一つの場所に集約し、これまで接点のなかった先輩と後輩の交流を生み出すとともに、質問と回答を次世代に引き継げる知識として蓄積する。

## 1.1 実現したい価値

| **価値の柱**         | **利用者にもたらす変化**                                              |
|----------------------|-----------------------------------------------------------------------|
| **つながりの創出**   | 在校生が、面識のない卒業生・先輩へ質問するきっかけを得られる。        |
| **知識・経験の継承** | 就活・履修・技術等のQ&Aを検索・再利用し、過去の経験が後輩の役に立つ。 |
| **学校との関係維持** | 卒業後も学校のお知らせ・イベントを通じて母校の近況と接点を保てる。    |
| **双方の参加価値**   | 卒業生は後輩支援、交流、キャリアにつながる機会を得られる。            |

## 1.2 最も重要な成果

成功の最優先基準は「在校生と卒業生の交流が増えること」とする。試験運用開始から最初の1か月で、在校生の質問に卒業生が1件以上回答した「質問の件数」を10件以上にすることを初期目標とする（質問⑪・⑮で合意）。

> **KPIの注意：**目標は企画上の設定値であり、参加人数、実証環境、学校の運用協力は未確定。人数・期間を踏まえて学校と評価条件を最終調整する。

# 02 背景と解決したい課題

企画の原点は、①卒業生に就職活動について質問できなかった、②先輩に履修登録を相談したかった、③技術的な疑問を気軽に聞ける先輩がほしかった、という在校生の実体験にある。最大の障壁は「質問方法がわからない」以前に、先輩・卒業生との接点そのものがなかったことである。

| **対象**   | **現状の課題**                                       | **改善後の状態**                                       |
|------------|------------------------------------------------------|--------------------------------------------------------|
| **在校生** | 就活・履修・技術で相談先が見つからない。             | Q&Aから質問でき、検索で過去の回答も参照できる。        |
| **卒業生** | 母校との接点が薄れ、後輩に経験を伝える機会が少ない。 | 質問への回答・お知らせ・イベントを通じて関係が続く。   |
| **学校**   | 学年間の経験共有や卒業後の交流が属人的になりやすい。 | 認証・承認と安全管理の下で、交流基盤を継続運用できる。 |

## 2.1 独自性（既存SNSとの差異）

- 学校が承認した関係者だけが閲覧でき、本人確認と権限管理を伴う。

- 「会話が流れて終わる」だけでなく、Q&Aを検索できる学校固有の知識として蓄積する。

- Q&A・お知らせ・イベントが一つに集まり、オンライン・対面の交流へつながる。

- 卒業予定者が卒業後も同一アカウントと過去の投稿を保持し、質問する側から回答する側へ移行できる。

# 03 利用者と主な利用シーン

| **利用者**       | **代表的な利用シーン**                                                  |
|------------------|-------------------------------------------------------------------------|
| **在校生**       | 就活・履修・技術の質問を投稿する／過去のQ&Aを探す／イベントを見つける。 |
| **卒業予定者**   | 在校生として質問・交流し、本人希望で卒業生検索にも掲載する。            |
| **卒業生**       | 得意分野のQ&Aへ回答する／学校近況を見る／お知らせ・イベントを申請する。 |
| **学校職員**     | 公式のお知らせやイベントを公開し、学校と卒業生の接点を維持する。        |
| **学校管理者**   | 登録・本人確認、管理者任命、監査、学校専用の通報案件を管理する。        |
| **アプリ管理者** | 権限の許す範囲でお知らせ・イベント審査、通常通報対応を行う。            |

※「卒業予定者」は基本所属が在校生の特別な状態。学校管理者／アプリ管理者は所属区分とは別軸の管理権限である。

## 5.1 Q&Aを中心とした体験設計

- 質問の投稿手順をわかりやすくする。回答者は検索・カテゴリー・絞り込みで自分が答えられる質問を見つける。

- カテゴリは既存仕様の「就職・キャリア」「技術・学習」「制作・プロジェクト」「雑談」の4分類を前提とする。

- 履修登録の相談は利用ニーズに含まれるが、専用カテゴリの追加は未確定。分類の見直しは別途仕様変更として判断する。

- 解決状態は質問者本人だけが何度でも変更でき、解決済みでも回答は継続可能とする。

## 5.2 明確にMVP対象外とするもの

学校外への公開、個別DM、Microsoft 365必須認証、イベントのアプリ内参加申込・出欠管理、決済、Q&A画像・ファイル添付、通常メール・プッシュ通知、お知らせのコメント・返信・いいね、イベント・お知らせの通報は含めない。

# 06 権限・承認・安全運用の前提

| **観点**           | **要望・制約**                                                                                               |
|--------------------|--------------------------------------------------------------------------------------------------------------|
| **利用者の承認**   | 本人確認情報と公開プロフィールを分離。初回登録審査は学校管理者のみ。承認前は申請状況のみ閲覧。               |
| **投稿権限**       | 在校生はお知らせ投稿不可。卒業生のお知らせ・在校生／卒業生イベントは審査制。学校職員の投稿は即時公開。       |
| **管理の分離**     | 学校管理者がアプリ管理者を任命・解除。アプリ管理者は自分の申請を承認・却下できない。                         |
| **強制非表示**     | 学校公式・学校職員イベントの強制非表示／復元は学校管理者のみ。卒業生お知らせ・一般イベントは条件付きで双方。 |
| **通報の独立性**   | アプリ管理者を対象とする通報は学校管理者のみ対応。削除済み証拠と操作ログの閲覧も学校管理者のみ。             |
| **状態による制限** | アカウント停止・プロフィール非表示・対象コンテンツ状態等を優先し、管理権限だけで拒否条件を上書きしない。     |
| **サーバー認可**   | UI非表示だけでなくAPI／DB側でも最新の権限を評価。ロール解除後は管理APIを即時拒否。                           |

> **整合性：**お知らせ・イベントの承認待ち編集申請は、承認まで旧公開版を維持する。監査ログ・証拠・削除済みお知らせには異なる閲覧権限と保存期間を適用する。

15ラリーでは既存MVPの全機能をデータ管理対象とすることを選択した。次の表は要望を実装に橋渡しするための「論理データ群とテーブル候補」であり、物理テーブル名・列・キー・インデックス・正規化・RLS等は設計段階で確定する。

## 8.1 主な関係・整合性

- ユーザー1人にプロフィールと投稿・回答・通知が関連する。質問には複数の回答・返信が紐付く。

- お知らせ／イベントの公開本体と承認待ち編集版を分離し、審査中の内容を一般公開しない。

- 通報案件は対象と対応履歴・証拠に関連し、担当管理者が権限を失った場合は学校管理者専用の引継ぎ待ちへ移す。

- 検索・統計集計は個人情報と一般公開情報を分離したアクセス条件で実行する。

## 8.2 保持期限とアクセス制御

| **データ**                   | **既存要件による保持期限／閲覧条件**                                                |
|------------------------------|-------------------------------------------------------------------------------------|
| **削除済みお知らせ本体**     | 削除から180日。投稿者本人・学校管理者のみ閲覧可能。期限後は本人向け一覧からも除外。 |
| **通報案件記録**             | 案件終了から1年。権限内管理者のみ、アプリ管理者対象案件は学校管理者専用。           |
| **削除された通報対象の証拠** | 関連する最後の案件終了後180日。学校管理者のみ閲覧可能。                             |
| **管理者操作ログ**           | 操作から1年。学校管理者のみ閲覧可能。一般管理画面から変更・削除不可。               |

## 9.1 非機能要件

- 承認済みの学校関係者のみ閲覧可能とし、非公開本人確認情報へのアクセスを厳格に制限する。

- 監視・バックアップ・障害復旧・保存期限に基づく削除処理の運用方式を詳細設計で決定する。

# 10 成功指標・試験運用の評価

**PRIMARY KPI**

試験運用開始後1か月で「在校生が作成した質問のうち、卒業生からの回答が1件以上付いた質問」を10件以上とする。質問数で数えるため、同じ質問に卒業生が複数回答しても1件として集計する。

| **指標**               | **定義・判定方法**                                                | **扱い** |
|------------------------|-------------------------------------------------------------------|----------|
| **主要KPI**            | 在校生作成質問に卒業生回答が付いたユニークな質問件数 ≥ 10／初月。 | 今回合意 |
| **補助：卒業生回答数** | 卒業生によるQ&A回答の総件数。                                     | 参考指標 |
| **補助：交流利用者数** | Q&Aで質問・回答の関係が成立した在校生・卒業生の人数。             | 参考指標 |
| **補助：イベント交流** | 在校生・卒業生向けイベントの開催実績。                            | 参考指標 |

集計時はテスト用投稿を除外し、当時の所属区分を判定できるようにする。開始日・評価対象の参加者数・イベントの集計方法は試験運用計画で確定する。イベントはMVPでアプリ内出欠管理を行わないため、参加人数の自動集計は前提にしない。

# 11 実装・検証の進め方

本書で選んだ範囲はMVP全領域であり、授業期間内にすべての運用要件を完成させるという意味ではない。既存方針に沿ってPoCで主要機能と権限管理を先に検証し、学校との合意後に段階的にMVPへ進める。

| **段階**              | **中心作業**                                                                        | **完了の確認**                        |
|-----------------------|-------------------------------------------------------------------------------------|---------------------------------------|
| **Phase 0／承認準備** | 学校へ企画提案、本人確認・運用体制・責任分担を協議。                                | 学校との合意事項を明文化。            |
| **PoC／先行検証**     | 認証・登録、Q&A、プロフィール、お知らせ／イベント審査、通知、通報、権限変更を試作。 | 主要な権限制御と利用導線が機能する。  |
| **MVP／段階実装**     | 既存v1.1の8領域を優先順位に沿って実装し、状態遷移・監査・保存期限も整える。         | 既存の受入条件と権限テストに合格。    |
| **限定試験運用**      | 在校生・卒業生・学校職員による試用とQ&A交流を実施。                                 | 初月KPIと利用者フィードバックを確認。 |

## 11.1 想定する主要な受入確認

- 未承認利用者がQ&A・お知らせ・イベントの画面／APIを閲覧できない。

- 在校生の質問に卒業生が回答し、検索・返信・解決状態の表示が正しく動く。

- 卒業生お知らせ／学生・卒業生イベントの未承認内容が一般公開されず、審査後に公開される。

- アプリ管理者は自己申請を承認できず、権限解除後は管理APIを即時利用できない。

- 通報・強制非表示・引継ぎ・監査閲覧の権限がロール・対象状態に一致する。
