【PRタイトル命名ルール】
形式：type: #Issue番号 変更内容

例：
feat: #12 ログイン画面を実装
fix: #15 ログインエラーを修正
docs: #18 API設計書を更新

type一覧：
feat     : 新機能追加
fix      : バグ修正
docs     : ドキュメント変更
refactor : コード整理（機能変更なし）
chore    : 環境構築・設定変更・その他の保守作業

## 概要
このPRで行った変更の目的を簡潔に記載


## 変更内容
変更した内容を箇条書きで記載

-

## 動作確認
確認できた項目にチェックを入れる

- [ ] ローカル環境で正常に起動する
- [ ] 変更した機能が正常に動作する
- [ ] エラー・例外時の動作を確認した
- [ ] 他の機能に影響がないことを確認した

### 確認結果
実際に確認した操作・結果を記載


## 影響範囲
該当する項目にチェック

- [ ] 画面・UI
- [ ] API・サーバー処理
- [ ] DB・マイグレーション
- [ ] 認証・認可・権限
- [ ] 設定・環境変数
- [ ] ドキュメント
- [ ] その他

## レビュー時に確認してほしい点
特に確認してほしい部分を記載。なければ「なし」


## PR作成前チェックリスト

- [ ] PRタイトルの命名ルールを守っている
- [ ] 関連Issueを紐づけている
- [ ] 不要なファイルが含まれていない
- [ ] パスワード・APIキーなどの機密情報を含めていない
- [ ] 必要な動作確認を実施した

---

## GitHub右側の設定ルール

各項目は本文に名前を書かず、GitHub右側で設定する

- [ ] **Reviewers**：PR作成者以外のメンバーを1人以上指定
- [ ] **Assignees**：原則PR作成者本人を指定
- [ ] **Labels**：変更内容に合わせて設定
- [ ] **Projects**：チームのGitHub Projectを設定
- [ ] **Milestone**：対象Sprintを設定（使用時のみ）
- [ ] **Development**：関連Issueを紐づける

【マージルール】
・原則1人以上のレビュー承認を得る
・指摘事項を修正してからマージする
・必要なチェックが通過していることを確認する
・mainへの直接Pushは原則行わない
