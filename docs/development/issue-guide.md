# After School Project Issue作成ガイド

## 1. このガイドの目的

このガイドは、After School Projectの開発Issueについて、チーム内で書き方を統一するためのものです。

開発全体の進め方は[開発・コントリビューションガイド](../../CONTRIBUTING.md)を参照してください。

担当者が「何を作るのか」「どの状態になれば完成なのか」「何を確認すればよいのか」を理解できるIssueの作成を目的とします。

## 2. Issueタイトルの付け方

GitHubのタイトル欄には、このIssueで実現・修正することを簡潔に記載します。

例：

- 学校発行アカウントでログインできるようにする
- プロフィールを編集できるようにする
- 質問を投稿できるようにする
- 卒業生がお知らせを申請できるようにする
- イベントを申請できるようにする
- Neonへ接続できるようにする

Issueタイトルには、`task:`や`[AUTH]`などの接頭辞を付けません。作業の種類や対象機能はLabelsで管理します。

Labelsは、種類（`feature`、`bug`、`docs`など）と対象機能（`auth`、`profile`、`qa`など）から、チームで使用するものを設定します。

## 3. 共通Issueテンプレート

GitHubでIssueを作成するときは「開発タスク」フォームを選択します。入力項目の定義は[task.yml](../../.github/ISSUE_TEMPLATE/task.yml)で管理します。

以下は、本文を直接記入する場合にも使える記入例です。説明文は具体的な内容に置き換え、任意項目は必要なものだけ残します。

小さな文書修正や保守作業では、「目的」「実装・変更すること」「受入条件」「確認方法」を基本とし、不要な節は省略できます。

```markdown
## 目的

誰が、何をできるようにするか、または何を改善するかを記載します。
必要に応じて、現在の課題や背景も記載します。

## 実装・変更すること

このIssueで行う作業を記載します。

- [ ] 作業内容：
- [ ] 作業内容：

## 対象範囲

- 対象：PoC / MVP / 共通（該当するものを残す）
- 対象外：今回対応しない機能や作業を記載します。なければ「なし」。

## 関連する要件・設計（任意）

関係する項目だけ残し、参照先のリンクと節名を記載します。
PoCとMVPで仕様が異なる場合は、今回適用する決定を明記します。

- 要件ID：
- 決定ID：
- 画面ID：
- API ID：
- 関連テーブル：
- 参照資料：
  - [資料名](URL)「節名」

## 受入条件

このIssueを完成と判断できる条件を記載します。
「どの状態で、何をすると、どうなるか」が分かる文章にします。
該当する正常系・異常系・権限や状態による制限を含めます。

- [ ] AC-01：
- [ ] AC-02：

## 確認方法

各受入条件を確認するための前提・操作・期待結果を記載します。
既存のテストや確認手順で確認できる場合は、その参照先を記載します。

- AC-01：
- AC-02：

## 依存関係・確認事項（任意）

関係する項目だけ残します。
着手や完成の判断を妨げる未決事項は、その影響を明記します。

- 先行Issue：#番号（先に完了する必要がある理由）
- 関連Issue：#番号
- 確認事項：
- 未決事項による影響：
```

## 4. 各項目の意味

### 4.1 目的

このIssueを作る理由です。

「誰が」「何をできるようになるか」、または改善する内容を記載します。文書修正や保守作業では、解決したい課題を記載します。

例：

> 利用者が、学校から発行されたアカウントでログインできるようにする。

### 4.2 実装・変更すること

担当者が行う作業です。

画面、ボタン、API、DB処理など、必要な作業を記載します。チェックボックスにすると、作業の進み具合も確認できます。

例：

- [ ] ログイン画面を作る
- [ ] 認証APIを作る
- [ ] セッションを保存する

「ログイン処理を実装する」は作業、「有効なアカウントでログインするとホーム画面へ移動する」は受入条件です。作業と、その結果を分けて記載します。

### 4.3 対象範囲

今回の対象がPoC・MVP・共通のどれかと、このIssueでは対応しないことを記載します。作業が予定以上に広がることを防ぎ、別Issueとの境界を明確にします。

例：

- 対象：PoC
- 対象外：パスワード再発行は別Issueで対応する。

### 4.4 関連する要件・設計（任意）

担当者が実装時に確認する設計資料です。何を根拠に実装するかを示します。

- **要件ID**：必要な機能を表す番号
- **決定ID**：技術や運用について決めた内容の番号
- **画面ID**：実装する画面の番号
- **API ID**：使用または実装するAPIの番号
- **関連テーブル**：使用するデータベースのテーブル
- **参照資料**：詳しい仕様が書かれている資料へのリンクと節名

すべてのIssueに全項目が必要とは限りません。関係する項目だけ残します。GitHub Issueから参照できるリポジトリ内の資料URLを使用します。

PoCとMVPで仕様が異なる場合は、今回適用する決定IDと参照先を明記します。PoC範囲は[PoC実装ロードマップ](../After_School_Project_PoC実装ロードマップ_v0.2.md)の「PoC範囲の決定記録」を確認します。

### 4.5 受入条件

Issueを完成と判断する条件です。

担当者と確認者が、同じ基準で完成を判断できるようにします。「前提となる状態・操作・期待する結果」が分かる文章にし、該当する正常系・異常系・権限や状態による制限を含めます。

`AC-01`などの番号は、受入条件と確認方法を対応させるためのものです。項目数は変更内容に合わせて増減します。

例：

- [ ] AC-01：有効な学校発行アカウントでログインすると、ホーム画面へ移動する。
- [ ] AC-02：誤ったパスワードではログインできず、エラーを表示する。
- [ ] AC-03：停止中のアカウントではログインできない。

### 4.6 確認方法

各受入条件を確認するための前提・操作・期待結果を記載します。受入条件の番号に対応させ、確認漏れを防ぎます。

- **受入条件**：どうなれば完成か
- **確認方法**：完成したことをどう確かめるか

例：

- AC-01：有効なテストアカウントのログインIDと正しいパスワードを入力し、ホーム画面へ移動することを確認する。
- AC-02：未ログインの状態で誤ったパスワードを入力し、エラーが表示され、保護された画面を利用できないことを確認する。
- AC-03：未ログインの状態で停止中のテストアカウントによるログインを試み、保護された画面を利用できないことを確認する。

既存のテストや詳細な確認手順がある場合は、その参照先を記載して構いません。

Issueには、着手時点で合意する条件と確認方法を記載します。実際に行った操作やテストの結果はPRに記載します。

### 4.7 依存関係・確認事項（任意）

ほかの作業との関係や、まだ決まっていないことを記載します。

- **先行Issue**：先に完了している必要があるIssue
- **関連Issue**：同じ機能に関係するIssue
- **確認事項**：チームで相談または決定する必要があること
- **未決事項による影響**：未決事項が着手や完成の判断を妨げるか、どの作業に影響するか

関係する項目だけ残します。先行Issue・関連Issueは、タイトルだけでなくIssue番号やURLを記載します。

例：

```markdown
- 先行Issue：#123 DB接続の整備（ログイン処理で認証情報を取得するため）
- 関連Issue：#124 ログアウト機能
- 確認事項：ログイン失敗時の表示文言
- 未決事項による影響：処理の実装には着手できるが、文言の決定が画面の受入確認に必要。
```

## 5. 各項目の役割

| 項目 | 書く内容 |
|---|---|
| 目的 | なぜ作るのか |
| 実装・変更すること | どの作業を行うのか |
| 対象範囲 | PoC・MVP・共通のどれか、何を対象外にするか |
| 関連する要件・設計（任意） | 何を参考にし、どの決定を適用するのか |
| 受入条件 | どうなれば完成か |
| 確認方法 | どうやって完成を確認するか |
| 依存関係・確認事項（任意） | ほかの作業や未決定事項、その影響 |

## 6. Issueを作成するときの注意

- 1つのIssueに複数の大きな機能を詰め込みすぎないようにします。
- 担当者が1つの作業として進められる大きさを目安にします。
- 受入条件は「適切に動作する」のような曖昧な表現ではなく、確認できる状態を記載します。
- 関連する要件・設計が分からない場合は、推測せず確認事項へ記載します。
- パスワード、トークン、データベース接続情報などの秘密情報はIssueへ記載しません。

## 7. 不具合報告との使い分け

このテンプレートは、実装・文書修正・保守作業などの開発タスクを整理するためのものです。不具合を報告するときは、GitHubで「不具合報告」フォームを選択します。定義は[bug_report.yml](../../.github/ISSUE_TEMPLATE/bug_report.yml)で管理し、次の項目を記載します。

- 不具合の概要
- 再現手順と前提条件
- 期待する動作
- 実際の動作
- 発生環境（ブラウザー、OS、アプリのバージョンなど）
- 必要に応じて、機密情報を除いたログやスクリーンショット

再現手順が不明な場合は、発生時の操作・頻度・分かっている条件を記載します。修正方針や原因の特定は、報告時点では必須ではありません。
