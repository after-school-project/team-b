## 1. 選定の前提

PoC範囲は[実装ロードマップの決定記録](./After_School_Project_PoC実装ロードマップ_v0.2.md#poc-scope)に従う。学校側が架空の全利用者アカウントを事前発行し、所属と管理権限を別々に設定する。メール所有確認、自己登録、登録審査、初回認証情報設定画面、パスワード回復画面は後続の対象となる。

操作条件は[画面一覧設計書 v0.2](./After_School_Project_PoC_画面一覧設計書_v0.2.md)、原要件は[MVP機能要件定義書 v1.1](./After_School_Project_MVP機能要件定義書_v1.1.md)と[権限詳細設計書 v1.0](./After_School_Project_ロール・権限マトリクス詳細設計書_v1.0.md)を参照する。

## 2. 採用する技術構成

| 項目 | 採用技術 | 選定理由・担当範囲 |
|---|---|---|
| 実行環境・言語 | Node.js 24.x・TypeScript | 既存のNode.js・TypeScript指定を具体化。ローカルとVercelでメジャー版を揃える |
| 画面UI | React・TypeScript（TSX） | 画面・フォーム等をReactコンポーネントで実装する |
| Webフレームワーク | Next.js App Router | 画面とサーバー処理を同じプロジェクトで管理する |
| 認証 | Better Auth・usernameプラグイン | ログインID・パスワード、CookieとDBによるセッション管理を担当する |
| DB | Neon PostgreSQL | 既存指定。認証データとアプリデータを保持する |
| DBアクセス | Drizzle ORM・node-postgres（pg） | 型付きのDB操作、認可に必要な条件付き更新、トランザクションを扱う |
| スキーマ変更 | Drizzle Kitのマイグレーション | 認証用・アプリ用スキーマの変更を同じ履歴で管理する |
| 配置 | Vercel・Node.js runtime | 既存指定。認証とDB処理をNode.js上で動かす |
| 開発ツール | VSCode・npm | VSCodeは既存指定。npmのロックファイルで依存関係を固定する |

Next.jsはReactを使うWebフレームワークで、画面をReactコンポーネントとして実装する。Reactを画面UIとして明示的に採用し、App Routerによる画面構成とサーバー処理を組み合わせる。[Next.js公式資料](https://nextjs.org/docs)

Next.jsとの公式連携とDrizzleアダプターが提供されている。今回の選定では、既存のTypeScript・Neon指定に合わせて認証も同じアプリ・DB内で管理できる点を採用理由とする。[Next.js連携](https://better-auth.com/docs/integrations/next)、[Drizzleアダプター](https://better-auth.com/docs/adapters/drizzle)

Node.js 24.xはVercelの対応ランタイムとして確認した。Next.js・React・react-dom・Better Auth・DrizzleとCLIの具体的なバージョンは、基盤構築時にNext.jsの対応条件と各パッケージの互換性を確認し、package.jsonとpackage-lock.jsonへ記録する。導入するバージョンに対応した公式ドキュメントを使用する。[VercelのNode.js対応](https://vercel.com/docs/functions/runtimes/node-js/node-js-versions)、[Next.jsのReactバージョン](https://nextjs.org/docs#react-version-handling)

## 3. ログインとアカウントの扱い

学校発行のログインIDと個別パスワードを採用する。ログインIDは公開表示名と分け、例として `poc_s001` を使う。小文字英数字とアンダースコアの3〜30文字とし、正規化後の一意性をDBで保証する。所属・管理権限・本人確認情報は認証済みの利用者IDに関連付け、ログインフォームから変更できないようにする。

Better Authのusernameプラグインはメール・パスワード認証を拡張するため、内部のユーザーレコードにはメール欄も必要になる。架空データのPoCでは `poc_s001@example.invalid` のような架空メールを内部管理用に設定する。メール確認状態は未確認のまま保持し、学校による利用資格確認済みの状態をアプリ側で別管理する。ログインIDはプラグインの仕様に従って正規化する。[usernameプラグイン](https://better-auth.com/docs/plugins/username)、[認証データモデル](https://better-auth.com/docs/concepts/database)

PoCではメール確認をログイン条件にしない設定を明示する。MVPへ移行する際は、同じ利用者IDとの関連付けを維持しながら、実際のメールアドレスの登録・所有確認と登録審査の扱いを別途設計する。

公開する認証経路はログインIDによるログイン、セッション確認、ログアウトを基本とする。オンライン用設定では `disableSignUp: true` とし、メールログイン、登録、利用者名・メール変更、退会などの認証エンドポイントの公開範囲をルート側でも制御する。実装時に採用版の全エンドポイントを照合し、学校の事前発行やプロフィール審査を迂回する更新経路を遮断する。[Better Authの設定](https://better-auth.com/docs/reference/options)

## 4. 発行・配布・再発行

| 操作 | 方針 |
|---|---|
| 初期発行 | 開発担当が学校発行用のコマンドを手元で実行し、全所属・管理権限のテストアカウントを作る |
| 認証情報 | 暗号学的乱数による24文字の個別パスワードを発行する。アプリの受入範囲は12〜128文字とする |
| 配布 | 実演参加者へ手元で個別に渡す。担当者・受渡方法の具体化は実演準備で行う |
| 忘れた場合 | 開発担当が対象の架空アカウントを確認し、コマンドで新しいパスワードを発行して個別に渡す |
| 再発行の効果 | 利用者ID・所属・投稿を維持し、古いパスワードと既存セッションを無効化する |
| 再実行・途中失敗 | 同じログインIDの既存アカウントと関連付けを確認する。通常の初期投入の再実行ではパスワードや管理権限を上書きしない。未完了の発行状態ではコミュニティ利用を許可しない |
| 記録 | 操作日時・対象ID・実行者・結果を記録する。平文パスワードはソース・DB・通常ログへ保存しない |

初期発行は、HTTPに公開しないコマンド専用の認証設定からBetter Authの正規作成処理を呼ぶ。オンライン用の登録禁止設定を切り替える運用は行わない。パスワード保存はライブラリのハッシュ処理を利用する。再発行の具体的なAPIと原子的な更新方法は採用版で検証し、失敗時に認証情報とセッションの状態が矛盾しないよう設計する。[メール・パスワード認証](https://better-auth.com/docs/authentication/email-password)

この再発行は架空アカウントを使うPoCの実演運用。実運用の学校管理者の緊急復旧・担当者の追加や退任はAUTH-23の学校協議で決める。

## 5. セッションと共通認可

次の設定値は今回の設計判断として採用する。

| 項目 | 方針 |
|---|---|
| セッション | NeonのDBに保存し、Cookieでセッション識別子を渡す |
| 有効期間 | 発行から8時間。利用による自動延長は行わない |
| Cookie | HTTPS上でSecure・HttpOnly・SameSite=Laxを適用し、Better AuthのOrigin・CSRF保護を利用する |
| Cookieのセッションキャッシュ | 無効。保護された取得・更新のたびにサーバーでDB上の有効性を確認する |
| 操作の認可 | 共通のサーバー処理で、最新の所属・管理権限・停止・プロフィール・所有者・対象状態を取得して判定する |
| 権限解除 | アプリ管理者権限の解除後もログインと基本所属を維持し、管理操作を即時拒否する |
| 停止 | 停止案内とログアウトを可能にし、通知を含むコミュニティ・管理機能を拒否する |
| 更新時の競合 | 更新のトランザクション内でも権限・対象状態を確認し、管理権限変更や審査確定と競合する更新を制御する |
| 返却データ | 各画面に必要な項目に絞る。学校専用の本人確認情報・削除後証拠・監査ログを他の利用者へ返さない |

Better AuthはDBセッションと有効期限設定を提供する。Cookieキャッシュを有効にすると、失効済みセッションの再検証に遅延が生じ得るため、本PoCはキャッシュ無効を選ぶ。8時間の固定有効期間はPoC用の設計値。[セッション管理](https://better-auth.com/docs/concepts/session-management)

Next.jsの画面入口でのチェックに加え、データ取得・更新の共通処理で認可を確認する。学校独自の所属・管理権限・停止状態をアプリのDBモデルで管理する。認証ライブラリのユーザー名や汎用管理者ロールから学校の操作権限を推定しない。[Next.jsの認可設計](https://nextjs.org/docs/app/guides/authentication)

ログイン失敗はIDの存在を判別できない共通表示にする。ブラウザーのログインはBetter AuthのHTTPハンドラーを通し、認証リクエストの回数制限をDBに保存して複数のサーバー実行で共有する。学校の同一回線から複数人が使う点を踏まえ、具体的な閾値は実演人数を含めて基盤構築時に調整する。サーバーから `auth.api` を直接呼ぶ処理を追加する場合、その呼び出しにはライブラリのHTTP回数制限が適用されないため、同等の制限を設ける。[認証の回数制限](https://better-auth.com/docs/concepts/rate-limit)

PoCは学校管理者・アプリ管理者を含め全員パスワード認証とする。多要素認証はMVP段階で要否・対象・復旧方法を再検討する（TECH-03）。

## 6. DB接続とマイグレーション

アプリ実行時はNeonのプール接続、マイグレーション等の管理用コマンドは直接接続を使用する。Drizzleのトランザクションで、審査の条件付き確定・状態変更・監査記録をまとめて扱う。セッション単位で設定が残ることを前提とする処理はプール接続へ持ち込まない。[Neonの接続プール](https://neon.com/docs/connect/connection-pooling)、[DrizzleとPostgreSQL](https://orm.drizzle.team/docs/get-started-postgresql)

認証スキーマは採用版のBetter Auth CLIで生成し、Drizzle Kitでマイグレーションを適用する。usernameと回数制限の追加スキーマを含め、生成内容を確認する。アプリ用の所属・管理権限・プロフィール等のスキーマと参照関係をER図で具体化する。[Drizzleアダプター](https://better-auth.com/docs/adapters/drizzle)

アプリからのDB取得はサーバー側を経由させる。DBの制約・アプリの認可条件・トランザクションを組み合わせ、ブラウザーへDB接続情報を渡さない。

## 7. 環境の方針

ローカル開発とPoC実演でDBと認証用秘密値を分ける。サーバーの設定項目は、実行用DB接続、管理コマンド用の直接DB接続、Better Authの秘密値、アプリの正規URLとする。公開URLを確定した後、認証の許可Originを具体的なURLで設定する。別環境のセッションを受け入れないことを基盤構築で確認する。

## 8. 基盤構築での確認条件

- 学校発行した各所属・管理権限のアカウントでログイン・ログアウトできる。
- 未発行ID、誤ったパスワード、自己登録API、メールログイン、許可していない認証更新経路を拒否できる。
- 8時間の期限切れ、ログアウト、パスワード再発行後に古い認証情報を利用できない。
- アプリ管理者権限を解除した直後、同じセッションの管理操作は拒否され、基本所属の許可操作は利用できる。
- 停止中は通知の取得・件数・既読更新も拒否し、プロフィール非表示中のアプリ管理者は管理操作できない。
- 複数のリクエストが競合しても、二重審査や権限変更後の不正な更新が成立しない。
- 初期発行の再実行・途中失敗・再発行の失敗でも、既存利用者との関連付けと認証状態に矛盾が生じない。
- ローカルとPoC用URLでDB読み書きと認証Cookieが動作し、環境間でセッションを共有しない。

公式資料上の連携可否を確認した段階。具体的なパッケージの組み合わせ、DB接続、Cookie、発行・再発行処理の実行確認は基盤構築で行う。
