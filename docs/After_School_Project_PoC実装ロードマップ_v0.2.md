本節を現行PoC範囲の参照先とする。監査CR-01〜03に対する企画者の今回の回答を反映した。従来のPoC-02〜07の選択記録と11月10日版の計画に衝突がある箇所は、本節の決定を適用する。

| 決定 | 今回の採用範囲 | 根拠 |
|---|---|---|
| CR-01 アカウント | 全員分を学校側が事前発行。メール所有確認・自己登録・登録審査と関連通知はMVPへ送る。職員の個別作成画面と初回認証情報設定画面もPoC対象外 | 企画者回答・ロードマップ案 |
| CR-02 Q&A・プロフィール | 制限Markdown、カテゴリー検索、本人Q&A投稿一覧、任意項目の詳細公開設定、検索掲載希望、再公開審査、卒業予定者の一括区分変更・誤変更修正をPoCに含める | 企画者回答・画面一覧案 |
| CR-03 お知らせ・イベント | 新規投稿・審査、取り下げ、公開後編集・再承認・旧版維持、お知らせ本人削除、イベント本人中止・開催終了、強制非表示・復元をPoCに含める | 企画者回答・ロードマップ案 |
| CR-08 申請操作 | 両機能の却下後修正・再申請、本人の取り下げ履歴も実装。取り下げ後の再開・コピーは提供しない。イベントの審査中修正は元の受付日時を維持 | CR-03の回答と既存MVP要件に基づく設計判断 |
| CR-05 学校管理者プロフィール | 学校管理者のプロフィールは非表示・再公開審査等の管理操作の対象外とする。学校管理者アカウントの停止・解除も既存仕様どおり対象外 | 企画者の追加回答 |
| 補完設計 | AD-14の簡易ログ一覧・詳細はPoC補完設計案。イベント自己申請の一覧表示はお知らせと揃える設計案 | 今回の資料調整における設計判断 |

学校による事前発行は、PoCで利用資格の確認を済ませた状態として扱う。所属・管理権限・有効状態を発行データで管理し、メール所有確認の実施状態と区別する。学校発行のログインIDと個別パスワードを使用し、開発担当がコマンドで発行・再発行する。認証情報は手元で個別配布する。全所属と管理権限の組み合わせに対応する架空アカウントを準備する。

## アカウント発行・認証の方針

| 項目 | 方針 | 状態 |
|---|---|---|
| メール認証 | メール所有確認・認証メール送信を実装しない | 確定 |
| アカウントの用意 | 学校側が利用者ごとにアカウントを用意する | 確定 |
| 自己登録・登録審査 | 学校側による事前発行を利用開始の前提とし、自己登録・登録申請・承認／却下・再申請をPoC対象外とする | 上記方針を反映 |
| ログイン方式 | 学校発行ログインID＋個別パスワード。メールを使うログイン経路は設けない | TECH-02で確定 |
| 発行の実装方法 | 開発担当がHTTPに公開しないコマンドで各アカウントと所属・管理権限を用意する | TECH-02で確定 |
| 配布・再発行 | 認証情報を手元で個別配布。忘れた場合は開発担当がコマンドで再発行し、旧パスワードと既存セッションを無効化 | TECH-02で確定 |
| 多要素認証 | PoCは全員パスワード認証。多要素認証はMVP段階で再検討する | TECH-03で確定 |

学校側による事前発行は利用資格の確認を済ませた状態として扱う。ログイン・セッション管理と操作ごとの認可はPoCで検証する。お知らせ・イベント・プロフィール再公開の審査は引き続き対象とする。本変更はPoC限定とし、MVPのメール確認・登録審査要件は維持する。

全所属・管理権限のテストアカウントを学校発行の想定で準備する。発行コマンドでは認証ライブラリの正規作成処理とパスワードハッシュを利用する。既存の利用者IDと所属・投稿を維持し、通常の初期投入の再実行で認証情報や管理権限を上書きしない。発行済みであることと、実際にメール所有確認を実施したことを区別する。

イベント終了は日時から判定し、保留中編集申請の取り下げは対象の読み書き時に反映するPoC案とする。定期処理を省略した制約は未実装一覧に残す。削除済みお知らせは期限後の閲覧を拒否し、物理消去は後続とする。

学校外公開、DM、決済、アプリ内参加申込、画像・ファイル添付、お知らせ・イベントへの通報は既存のMVP対象外として追加しない。PoC向けの省略・暫定方式は記録し、既存MVP要件と区別する。

## 実装中に守る条件

- **共通認可：** 画面非表示に加え、サーバー側で最新の所属・管理権限・アカウント・プロフィール状態を確認する。非公開の本人確認情報は公開プロフィールと分離する。
- **アカウント：** 自己登録の画面・公開エンドポイントを提供しない。利用者自身が所属・管理権限を指定してアカウントを発行できないようにする。
- **Q&A：** 解決状態の変更は質問者本人のみ。解決後も回答可能。質問削除後も回答・返信は原則残す。
- **審査：** 自己承認・自己却下を禁止し、並行確定を防ぐ。公開後の編集審査中は旧公開版を維持する。取り下げや削除・中止が確定した申請は審査できない。
- **申請の違い：** お知らせは審査中編集不可、イベントは修正可能。イベント修正でも最初の受付順を維持する。
- **イベント日時：** 過去開始日の新規申請は日付修正まで承認・却下不可。終了日時がなければ開始翌日00:00 JSTに終了し、終了後の編集・中止を拒否する。
- **状態の分離：** 審査・公開・削除・開催状態を分ける。編集承認で強制非表示を解除せず、復元で中止を取り消さない。
- **管理制限：** アプリ管理者対象案件・削除後の通報証拠・監査ログは学校管理者に限定する。管理機能喪失時などの担当案件引継ぎも実装する。
- **通知：** 通報者には受付完了を表示する。お知らせ公開の一斉通知と、お知らせ・イベントの強制非表示・復元の個別通知は送らない。

## PoCの完成チェック

- [ ] 学校側が用意した在校生・卒業生・学校職員・管理者のアカウントで主要な操作を実演できる。
- [ ] 未ログイン・停止中利用者・権限外の利用者による取得と更新をサーバー側で拒否できる。
- [ ] 学校が用意していないアカウントではログインできず、公開の自己登録経路も利用できない。
- [ ] 編集再承認・旧公開版維持、取り下げ・却下後再申請、お知らせ本人削除、イベント中止・終了、強制非表示・復元、引継ぎが仕様どおりに動く。
- [ ] 制限Markdown、本人Q&A投稿一覧、質問削除後の残存回答、詳細公開設定、非表示プロフィールの検索除外、卒業区分変更と履歴を確認できる。
- [ ] 学校管理者対象の停止・解除を拒否し、アプリ管理者本人に対する学校専用操作を制限できる。
- [ ] ホームの4領域と通知の未読件数を確認し、停止中は通知も含む取得・更新を拒否できる。
- [ ] 簡易ログ閲覧を実装する場合は学校管理者の一覧・詳細と、アプリ管理者の画面・API拒否を確認できる。
- [ ] 非公開情報・未承認版・削除後の証拠・監査ログの閲覧制限を確認できる。
- [ ] 再ログイン後もデータが残り、PoC用URLで同じ実演を再現できる。
- [ ] 起動・データ初期化・実演手順、テスト結果、未実装一覧が残っている。
