## 1. 適用順序

原要件は[権限詳細設計書](./After_School_Project_ロール・権限マトリクス詳細設計書_v1.0.md)と[MVP要件](./After_School_Project_MVP機能要件定義書_v1.1.md)。PoCの例外は[ロードマップ](./After_School_Project_PoC実装ロードマップ_v0.2.md#poc-scope)と[技術決定書](./After_School_Project_PoC_技術構成・認証方式決定書_v0.1.md)を適用する。本表はServer Component・Route Handler・Server Action・DB取得処理に共通して適用する。

| 順序 | 判定 | 満たさない場合 |
|---|---|---|
| 1 | DB上で有効な認証セッション、発行完了、学校による利用資格確認済み | 未認証は401相当で画面はAU-01。認証済みでも未発行・未完了・学校確認未完了は403 ACCOUNT_NOT_READYとし個人データを返さない |
| 2 | アカウントが停止中でない | 本人向け停止案内とログアウトを許可し、コミュニティ・通知・管理機能を拒否 |
| 3 | プロフィール状態が操作を許可する | 非表示中は本人プロフィール修正・再公開申請、通常閲覧、既存投稿の本人削除を許可。新規投稿・コメント・既存編集とアプリ管理機能を拒否 |
| 4 | 現在の基本所属と追加管理権限が操作を許可する | 管理エリアの資格不足は403相当。本人用データの他人による取得は404相当 |
| 5 | 本人・他人・投稿区分・対象者の管理権限などが条件を満たす | 条件外の対象・非公開項目を返さない |
| 6 | 対象の申請・公開・削除・開催・期限と自己操作の条件を満たす | 取得は状態案内または404相当。状態競合・更新番号の不一致は409相当 |

「本人」は認証セッションの利用者IDとDBの所有者IDの一致で判定する。送信されたactor ID・所属・管理権限は認可の根拠にしない。PoCの学校確認済み状態とメール所有確認状態を別に扱う。

利用者が明示的に要求する更新はPOST・PATCH・DELETE相当の処理に限定し、Origin・CSRF保護と入力スキーマを適用する。期限到来によるシステム側の状態同期はDB・ER設計書7節に従う。利用者別の取得結果や認可結果を、別の利用者にも返る共有キャッシュへ保存しない。

有効な管理者は、学校管理者、または停止・プロフィール非表示・権限解除の制限がないアプリ管理者。管理者も本人の基本所属による投稿条件を適用する。学校管理者の停止・解除とプロフィール管理操作は、企画者回答により対象外。

## 2. 共通・プロフィール・Q&A

| QA-02 | 本人の質問・回答等の削除 | 本人。プロフィール非表示中も可能。公開中の子投稿を連鎖削除しない。必要な証拠保全と引継ぎを同時に実行 | QA-05、PR-06、MD-15 |
| QA-02 | 未解決・解決済みの切替 | 質問者本人・プロフィール公開中・未削除。管理権限は他人の質問の切替を許可しない。解決後も回答可 | QA-04／10、AUTH-08 |
| QA-02 | Q&Aの強制非表示・復元 | 有効な両管理者。対象の投稿者がアプリ管理者なら学校管理者のみ。理由通知・監査記録を既定条件で生成 | QA-11、MD-08、AUTH-22 |

プロフィール非表示中は、申請本文修正・再申請・取り下げ・イベント中止などの既存コンテンツ変更にも制限優先型の規則を適用する。本人削除の対象はPoCで削除を提供するQ&Aと公開済みお知らせ。イベントには本人削除を設けない。

プロフィールの任意項目は、企画者回答により「全利用者に公開／本人のみ」を項目ごとに選ぶ。未設定は本人のみ。管理者向け再公開審査にも公開予定の項目だけを返し、本人のみの任意項目は返さない。学校管理者による本人確認情報の照会は別の専用権限で判定する。

サーバーで項目を絞ってから返し、非公開値をブラウザーへ送って表示だけを隠す処理は行わない。削除済み質問配下の残存回答・コメントへの返信は、その親投稿が閲覧・返信可能な状態なら許可する。

## 5. 更新・権限変更を同時に処理する条件

1. リクエストのセッションを確認し、必要な対象と利用者IDを特定する。
2. 更新トランザクション内で、実行者・対象者・投稿者・割当候補など認可に必要な利用者行をIDの昇順でロックする。PoCの初期実装は同じ `FOR UPDATE` を使い、途中でロックを昇格する順序差を避ける。
3. 対象行は本体 → 申請 → 案件の順、同じ分類ではテーブル名・IDの昇順でロックする。ロック後に追加の利用者依存が判明したらロールバックし、必要なIDを揃えて再実行する。
4. 最新の所属・権限・停止・プロフィール・対象状態・更新番号で本表を再判定する。権限やプロフィール状態の変更処理も同じ利用者行を最初にロックする。期限判定にはロック取得後のDBの現在時刻を使う。
5. 条件付き更新を行い、通知・履歴・監査・必要な証拠保全と引継ぎを同じトランザクションで記録する。確定件数が想定と違えば競合として処理する。
6. コミット後の要求には変更後の権限を適用する。既に処理中の更新と権限解除はロックで直列化する。操作の再送には同じ再送キーと内容を使用し、確定済みの結果を再認可して返す。

行ロックと一定の取得順序を用いる設計はPostgreSQLの機能に基づく。実際の索引・ロック範囲・再試行を基盤構築で確認する。[PostgreSQLの明示的ロック](https://www.postgresql.org/docs/current/explicit-locking.html)

## 6. 初期実装の受入条件

| 対象 | 成立させる確認 |
|---|---|
| セッション | 未認証・期限切れ・旧パスワード／再発行前セッションを拒否 |
| ホーム | 停止中の本文・件数・通知を返さず、管理権限外のカードを返さない |
| プロフィール | 他人の編集、所属・管理権限のフォーム改ざん、非公開項目を使った検索を拒否 |
| 非表示・再公開 | 非表示本人の修正保存と審査中再編集を許可し、古い版の承認を競合として拒否 |
| 管理権限 | アプリ管理者の解除後も一般ログインは維持し、次の管理要求を拒否 |
| 所有・対象者 | 他人の投稿・通知・申請を本人用のIDで取得・更新できない。学校専用案件と証拠も拒否 |
| 並行更新 | 自己審査、二重審査、期限後操作、取り下げ後の承認、権限解除と競合する更新を拒否 |

本書は実装契約。受入項目は基盤・各機能の実装時にAPI・DBを含めて検証する。
